# OCR エンジンの比べ方

[English](benchmark.md) | 日本語

`design.ja.md` の OCR エンジンを、架空の書類で比べるやり方。結果は `benchmark-results.ja.md` にあり、次のことを決めるのに使う:

- 主に使うエンジン（OS ごとに違ってよい）と、照合役のエンジン
- 前処理（傾きの補正など）が要るか、ページを画像にする解像度の決め方（`design.ja.md` の 1.）が妥当か
- 複数のエンジンの結果を照らし合わせると、読み違いをどれだけ見つけられるか
- GPU と CPU で結果・時間がどれだけ違うか

## 進め方

1. **動作の確認**: 各エンジンの worker（`workers/`）を各 OS に入れて、架空の書類を数枚 `ocr run` で読ませる。
   入れ方の問題（Python の版・CUDA・OS 専用の部品）を洗い出す。結果は目で見るだけで、数字は取らない。手順は
   `engine-setup.ja.md`
2. **比較**: すべての架空の書類をすべてのエンジンで読み（`ocr run`）、下の指標を出す（`ocr score-engines`）。
   時間がかかるので、バックグラウンドで放置する

入らない・動かないエンジンは、比較から外す（理由を結果に書く）。

## 環境とエンジンの組み合わせ

| エンジン | Mac | Windows | Linux |
|---|---|---|---|
| yomitoku | CPU・MPS | CUDA・CPU | CPU |
| yomitoku（`--lite`） | CPU | CPU | CPU |
| PaddleOCR（PP-OCRv6） | CPU | CUDA・CPU | CPU |
| NDLOCR-Lite | CPU | CPU | CPU |
| Apple Vision（ocrmac） | ○ | — | — |
| Windows の OCR | — | ○ | — |
| Tesseract（jpn） | CPU | CPU | CPU |

- 同じエンジンを CPU と GPU の両方で動かし、結果が一致するか・時間がどれだけ違うかを見る
- Linux は CPU 専用の基準にする。CPU の結果が 3 つの環境で一致するかも見る

## 評価用の架空の書類

### 作り方

`ocr make-samples` で作る（`src/scriptorium/samples.py`）:

```bash
uv run scriptorium make-samples data/benchmark --count 2          # 種類ごとに 2 通り × 劣化 16 通り = 128 ページ
uv run scriptorium make-samples data/benchmark --count 4 --seed 7 # 256 ページ。種を変えると別の値になる
```

- **すべて架空の値で作る**（CONTRIBUTING.md）。店名・品名・会社名は架空の一覧から、金額・日付・番号は乱数で作る
- 乱数の種（`--seed`）が同じなら、同じ書類ができる。1 つの書類の劣化違いは、同じ値になる
- Pillow で描く。フォントは各 OS の日本語のフォント（ヒラギノ・游ゴシック・メイリオ・Noto Sans CJK・IPA ゴシック）を
  探して使う。`--font` で指定もできる
- 書類ごとに、**正解**（行ごとの文字・位置・種類）を `<ファイル名>.truth.json` に書く。種類は `amount`（金額）・
  `date`（日付）・`number`（そのほかの数字）・`text`。位置はポイント（ページの左上から）で、劣化で回したり
  傾けたりしたときは、正解の位置も一緒に動かす
- 生成した画像・PDF はリポジトリに入れない（`data/benchmark/` などに作る）

### 書類の種類

| 種類 | 狙い |
|---|---|
| レシート（`receipt`、幅 80mm） | 小さい文字、右寄せの金額、値引のマイナス、注記 |
| カードの明細（`statement`、A4、罫線の表） | 表の中の文字、右寄せの金額、返金のマイナス、日付の列 |
| 請求書（`invoice`、A4、印影つき） | レイアウトの混在、印影と文字の重なり、大きい金額、請求番号 |
| 通帳風（`passbook`） | 行の多い表、カタカナの摘要、和暦の `YY-MM-DD`、残高の列 |

### 読み違えやすい文字を混ぜる

- 形の似た文字: 品名・店名に `カ`/`力`、`ロ`/`口`、`エ`/`工`、`ニ`/`二`、`へ`、`一`/`ー`、`0`/`O`、`1`/`l`/`I` を入れる
- 金額の表記: 桁区切りのカンマ、`¥`、`円`、マイナス（`-`・`△`・`▲`）、ときどき全角（`￥１，２３４`）
- 日付の表記: `2031/04/09`、`2031年4月9日`、和暦（`令和13年4月9日`、`R13.4.9`）、通帳の `13-04-09`
- 小さい注記（6.5〜7pt）、大きい合計・見出し

### 劣化のさせ方（`samples.VARIANTS`）

| 名前 | 劣化 |
|---|---|
| `300`・`150`・`200`・`600` | その解像度で描く（その解像度でスキャンしたもの） |
| `slant+1`・`slant-3` | 1 度・-3 度傾ける |
| `turned90`・`turned180` | ページごと 90 度・180 度回す |
| `jpeg50` | JPEG（品質 50） |
| `noise`・`blur`・`shadow`・`bw` | ノイズ・ぼかし・照明のむら・白黒の 2 値化 |
| `pdf`・`pdf150` | 画像だけの PDF（300dpi・150dpi） |
| `photo` | スマホで撮った風（2 度傾け、照明のむら・ノイズ、JPEG 品質 75） |

### 量

`--count 2` で 128 ページ、`--count 4` で 256 ページ。最初は `--count 1`（64 ページ）で流れを確かめる。

## 指標

### 比べる前に表記をそろえる

正解とエンジンの結果の両方に、同じそろえ方をしてから比べる（`design.ja.md` の 8. と共通にする）:

- Unicode の NFKC で、全角と半角をそろえる
- 空白を取り除く（日本語の文字の間の空白は、エンジンによって入ったり入らなかったりするため）
- 金額: `¥`・`￥`・`円`・桁区切りのカンマを取り除き、マイナスの表記（`-`・`△`・`▲`）を 1 つにそろえる
- 長音・ハイフンの類（`ー`・`－`・`‐`・`-`）は、文字の誤り率では区別し、数字の一致では区別しない

### 正解の行とエンジンの結果の対応のさせ方

エンジンごとに文字の塊の切り方が違うので、**正解の行を単位にして比べる**（`src/scriptorium/compare.py`）。
エンジンの塊は、それが半分以上載っている正解の行（高さの 1/4 だけ広げる）に入れる。どの行にも半分以上載って
いない塊は「ほかの所で読んだもの」（印影・罫線を文字と読んだものなど）として数える。行に入った塊を、エンジンが
読んだ順につないだものを、その行の読み取り結果とする（位置の順にしないのは、逆さまのページでは行が右から左に
進むため）。

1 つの塊が、同じ高さ（同じ行）の正解の行をいくつも、それぞれ半分以上含む（例: 「合計 …… ¥1,234」の項目名と金額を
1 つの塊に読む。NDLOCR-Lite は本のように 1 行をまとめて返す）ときは、その塊の文字を正解の行に分ける。分け方は、
正解の行を並びの順（逆さまのページなら逆の順）につないだものと、塊の文字の編集距離がいちばん小さくなる対応で決め、
間に余分に読んだ文字は前の行に付ける。高さの違う行（2 行にまたがる塊）は分けず、これまでどおり多く載っているほうの
行に入れる。

### 出す指標

`ocr score-engines` が出すのは、金額・日付の完全一致率、金額・日付の誤りの一覧、文字の誤り率、読み落とし、
ほかの所で読んだ数、1 ページあたりの時間（全体と劣化ごと）。

```bash
uv run scriptorium run data/benchmark -e yomitoku -e tesseract   # 読む（放置してよい）
uv run scriptorium score-engines data/benchmark                        # 読んだエンジンごとに採点する
```

| 指標 | 内容 | 重み |
|---|---|---|
| **金額・日付の完全一致率** | 種類が `amount`・`date` の行のうち、そろえた後で正解と完全に一致した割合 | 最重視 |
| **金額の誤りの件数** | 金額が違って読まれた件数（読み落としとは分ける）。1 件でも重く見る | 最重視 |
| 文字の誤り率（CER） | 編集距離 ÷ 正解の文字数。行ごとに出して全体で合計する | 重視 |
| 読み落とし率 | 対応する塊がない正解の行の割合 | 重視 |
| 余分な検出 | どの正解の行にも対応しない塊の数（印影・罫線を文字と読んだものなど） | 参考 |
| 位置の精度 | 正解の行の範囲と、対応した塊の範囲の重なり（IoU） | 参考 |
| 確からしさの役立ち方 | 確からしさが低い順に並べたとき、誤りのある行の何割が上位に集まるか | 参考（照合の設計に使う） |
| 時間 | 1 ページあたりの時間（モデルの読み込みは別に出す） | 参考（放置できるので重視しない） |
| メモリ | 最大の使用量（GPU のメモリも） | 参考（GPU のメモリの大きさで、載るモデルが決まる） |

## 実データでの確かめ（任意）

架空の書類で絞り込んだあと、手元の実データのスキャンでも試す。

- **実データとその結果は手元の外に出さない**（Issue にも書かない）。結果のメモにも、中身（金額・名前など）は書かない
- 実データには正解がないので、エンジン同士の一致率と、食い違った箇所を人が見て正しかったほうを数える
- 書けるのは集計した数字だけ（例:「食い違い 12 箇所のうち、yomitoku が正しかったのは 10 箇所」）

## 結果の残し方

- 比較の結果は `docs/benchmark-results.ja.md` にまとめる（架空の書類の結果だけ）。測った条件も一緒に書き、後で
  同じ条件で比べ直せるようにする: scriptorium の版（コミット）、各エンジンの版とモデル、装置、OS とその版、CPU・GPU の
  型番、メモリの量、設定。機械の仕様は個人情報ではないので書く。マシンのパス・ユーザー名・ホスト名は書かない
- 各エンジンの生の結果は `data/benchmark/` に残し、リポジトリには入れない
- エンジンの版が上がったり、新しいエンジンを足したりしたら、同じ書類で比べ直す（生成のスクリプトと乱数の種を
  固定してあるので、同じ書類を作り直せる）

## 決め方

- **主に使うエンジン**: 金額・日付の完全一致率が一番高く、金額の誤りが少ないもの。時間は、CPU でも
  1 ページ数分以内なら問題にしない（放置できるため）
- **OS ごとの既定**: すべての OS で動くエンジンを既定にする。Mac の Apple Vision のような OS 専用のものは、
  精度が上回るときだけ、その OS の既定の照合役にする
- **前処理**: 劣化のある書類で、前処理ありのほうがはっきり良いときだけ既定にする。ページの向きの判定
  （`--orient tesseract`）は、エンジンごとに付けた場合と付けない場合を比べ、`turned90`・`turned180` の差で決める
- **解像度**: 150dpi のスキャンを 300dpi に描き直したほうが良いかを確かめ、`design.ja.md` の解像度の範囲を見直す
- **照合**: 2 つのエンジンの食い違いで、金額の誤りの大半を拾えるなら、取り込みの前に食い違いを確かめる流れにする
