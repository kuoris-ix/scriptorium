# OCR エンジンの比較の結果

[English](benchmark-results.md) | 日本語

`benchmark.ja.md` の方法で、架空の書類を読ませた結果。架空の書類だけの結果なので、読み違えた値もそのまま載せている。

再現のしかたのコマンドは、clone の中で動かす `scriptorium` コマンドと、その設定（`SCRIPTORIUM_*`、README の
「試す」）で書いた。scriptorium の `ocr` コマンドを付けたプログラムでも同じ（`myapp ocr run` など。設定はその
プログラムのもの）。

## Tesseract（基準）

ほかのエンジンと比べる基準。Linux のコンテナの CPU で、ほかのエンジンより先に通した。

### 条件

| 項目 | 内容 |
|---|---|
| 日付 | 2026-10-08 |
| 環境 | Linux（Ubuntu 24.04、コンテナ）、CPU |
| エンジン | Tesseract 5.3.4（Ubuntu のパッケージ）、`jpn+eng`、psm 3（`workers/tesseract`） |
| 書類 | `ocr make-samples --count 2 --seed 1`（4 種類 × 2 通り × 劣化 16 通り = 128 ページ）、フォントは IPA ゴシック |
| 設定 | 既定（300〜600dpi） |

### 全体

| | 金額の完全一致 | 日付の完全一致 | 文字の誤り率 | 読み落とした行 | 1 ページの時間 |
|---|---|---|---|---|---|
| そのまま読む | 78.8%（1488/1888） | 85.0%（653/768） | 18.6% | 499/5264 | 1.4 秒 |
| `--orient tesseract` | **84.7%**（1600/1888） | **91.3%**（701/768） | 12.4% | 501/5264 | 1.2 秒（判定を除く） |

### 劣化ごと（金額の完全一致 / 日付の完全一致）

|---|---|---|
| `300` | 95.8% / 100% | 95.8% / 100% |
| `150` | 95.8% / 97.9% | 同じ |
| `200` | 94.9% / 100% | 同じ |
| `600` | 89.8% / 100% | 同じ |
| `slant+1` | 94.9% / 100% | 同じ |
| `slant-3` | 77.1% / 83.3% | 同じ |
| `turned90` | 95.8% / 100% | 95.8% / 100% |
| `turned180` | **0.8% / 0%** | **95.8% / 100%** |
| `jpeg50` | 93.2% / 100% | 同じ |
| `noise` | 94.9% / 100% | 同じ |
| `blur` | 89.0% / 97.9% | 同じ |
| `shadow` | 50.0% / 72.9% | 同じ |
| `bw` | 92.4% / 91.7% | 同じ |
| `pdf` | 94.1% / 100% | 同じ |
| `pdf150` | 94.1% / 100% | 同じ |
| `photo` | 8.5% / 16.7% | 同じ |

### わかったこと

- **180 度回ったページは、そのままではまったく読めない**（`17-06-28` を `82-90-L1` と、逆さまのまま読む）。
  90 度は Tesseract が自分で扱えた
- **`--orient tesseract`（向きを判定してから読む）で、180 度回ったページも回っていないページと同じだけ読めた。**
  回っていないページの結果は変わらない
- 向きの判定（Tesseract の OSD）:

  | | ページ数 |
  |---|---|
  | 正しい判定で、回した | 116（回す必要のあった 32 ページはすべて） |
  | 正しい判定で、確からしさが低く回さなかった | 6（どれも回す必要のないページ） |
  | 間違った判定で、確からしさが低く回さなかった | 6（ぼかしたページを 180 度と判定。確からしさ 0.6〜2.8） |
  | 間違った判定で、回した | 0（下限 5 のとき。下限 2 では 1 ページを間違って回し、`blur` の金額が 82.2% に下がった） |

  正しく回した判定の確からしさは 8.4 以上だったので、回す下限（`models.ORIENT_MIN_CONFIDENCE`）を 5 にした
- Tesseract が弱いのは、照明のむら（`shadow` 50%）、3 度の傾き（`slant-3` 77%）、スマホで撮った風（`photo` 8.5%。
  傾き・むら・ノイズ・JPEG が重なったもの）。傾きの補正やむらの補正の前処理が効くかは、ほかのエンジンの結果を見て決める
- 読み違えの例（そのまま読んだとき）: `¥3,438` → `\3.438`（¥ を `\`、カンマをピリオド）、`17,700` → `17,708`、
  `3,720` → `3,120`、全角の `￥３７，８１８` → `\ギっつ/,818`
- 600dpi は 300dpi より悪かった（89.8%）。描き直す解像度の上限 600dpi が高すぎないかは、ほかのエンジンでも確かめる

### 前処理（`--preprocess`）

どれも `--orient tesseract` を付けて読んだもの。

| | 金額の完全一致 | 日付の完全一致 | 文字の誤り率 | 読み落とした行 |
|---|---|---|---|---|
| 前処理なし | 84.7% | 91.3% | 12.4% | 503 |
| `flatten` | 90.0% | 93.8% | 8.4% | 274 |
| `deskew` | 85.6% | 93.0% | 11.0% | 428 |
| **`flatten,deskew`** | **93.2%** | **97.4%** | **5.0%** | **95** |

劣化ごとの金額の完全一致（変わったものだけ）:

| 劣化 | 前処理なし | `flatten` | `deskew` | `flatten,deskew` |
|---|---|---|---|---|
| `shadow` | 50.0% | 95.8% | 50.0% | 95.8% |
| `photo` | 8.5% | 42.4% | 5.1% | 75.4% |
| `slant-3` | 77.1% | 78.8% | 94.9% | 94.9% |
| `600` | 89.8% | 92.4% | 89.8% | 92.4% |
| `bw`（日付） | 91.7% | 83.3% | 91.7% | 83.3% |

- `flatten` で照明のむらが、`deskew` で傾きが、回っていないページと同じくらいまで読めるようになった。2 つを合わせると、
  傾きと照明のむらが重なる `photo` も 75% まで読めた
- 悪くなったのは、白黒の 2 値化（`bw`）の日付だけ（91.7% → 83.3%。`flatten` でグレースケールに戻すと、Tesseract が
  日付の数字を 1 つ取り違える）。ほかの劣化は変わらないか、少し良くなった
- 時間は、前処理の分だけ 1 ページ 0.3〜1 秒ほど増える（同じ環境で、ほかの処理と同時に動かしたので目安）
- Tesseract では `--orient tesseract --preprocess flatten,deskew` を使う。ほかのエンジン（自分で照明や傾きを扱うものも
  ある）でも要るかは、下の「Windows: 向きの判定と前処理」で同じように比べた

### 再現のしかた

```bash
uv run scriptorium make-samples data/benchmark --count 2 --seed 1
uv run scriptorium run data/benchmark -e tesseract
uv run scriptorium run data/benchmark -e tesseract --orient tesseract
uv run scriptorium score-engines data/benchmark -e tesseract
uv run scriptorium score-engines data/benchmark -e tesseract --orient tesseract
uv run scriptorium run data/benchmark -e tesseract --orient tesseract --preprocess flatten,deskew
uv run scriptorium score-engines data/benchmark -e tesseract --orient tesseract --preprocess flatten,deskew
```

フォントが違うと（ヒラギノ・游ゴシックなど）、書類の見た目と結果が少し変わる。同じ環境のエンジン同士で比べる。

読み落とした行の数は、同じ行の項目名と金額を 1 つに読む塊を分けて採点するようにした後（`benchmark.ja.md`）に
数え直したもの（2 行減った。金額・日付の数は変わらない）。

### わかったこと

- **PaddleOCR と yomitoku-lite がいちばん正確**: 金額 99.6〜99.7%・日付 100%。劣化のほとんどで満点で、GPU で 1 ページ
  0.5〜1 秒。明細などの書類には、まずこの 2 つを使い、`ocr diff-engines` で互いに照らし合わせる
- **yomitoku（通常のモデル）は逆さまのページに弱い**（`turned180` で金額 55.9%・日付 25.0%）。ほかはほぼ満点。
  軽いモデル（yomitoku-lite）は逆さまでも 96.6% 読めた。逆さまのページがありうるなら `--orient tesseract` を付ける
- **NDLOCR-Lite は 80.8%**: 「項目名 …… 金額」の 1 行をまとめて 1 つの塊に読む（採点では分けて比べる）。逆さま（0%）・
  3 度の傾き（55.9%）に弱い。ページごとにモデルを読み込み直していたので 1 ページ 9 秒かかった（その後、モデルを
  読み込んだままにして 0.7 秒ほどになった。`design.ja.md` の「速さ」）。
  本向けのエンジンなので、縦書きの本で改めて比べる
- **Windows の OCR は速い**（1 ページ 0.2 秒）が、ぼけ（18.6%）・写真（66.1%）・3 度の傾き（33.9%）・回したページに弱い
- **Tesseract は 66.2%**: Linux の 78.8% より低いのは、フォント・Tesseract の版・書類の数が違うため（同じ環境のエンジン
  同士で比べる）。照明のむら（32.2%）・写真（0%）に弱いのは Linux と同じ
- 逆さまのページは、yomitoku-lite と PaddleOCR のほかは読めない。向きの判定と前処理（`--orient tesseract --preprocess
  flatten,deskew`）を付けた結果は、下の「Windows: 向きの判定と前処理」

### わかったこと

- **向きの判定で、逆さま・横向きのページはどのエンジンも回っていないページと同じだけ読めた**（yomitoku の `turned180`
  55.9% → 100%、NDLOCR-Lite・Windows の OCR・Tesseract は 0% → 94.9〜98.3%）。回す必要のある 8 ページはすべて正しく回し
  （確からしさ 6.74〜23.48）、ぼけたページ 2 枚を 180 度と判定したもの（確からしさ 0.09・2.2）は下限 5 より低く、回さなかった
- **Windows の OCR は前処理がよく効く**（77.0% → 92.4%）: 3 度の傾き 33.9% → 98.3%、写真 66.1% → 84.7%。ぼけ（18.6%）は
  前処理では変わらない
- **Tesseract も 66.2% → 82.5%**: 照明のむら 32.2% → 93.2%、写真 0% → 62.7%。Linux で決めた `--orient tesseract
  --preprocess flatten,deskew` が Windows でも効く
- **PaddleOCR は前処理で悪くなった**（99.7% → 98.5%）: 照明のむらを補正した `invoice-1-shadow` を 1 つも読まなかった
  （そのままなら 39 個）。`shadow` の読み落とし 38 行はこの 1 ページ。ほかの書類の `shadow` は前処理を付けても読めた
  （下の 256 ページの節）

  yomitoku の中の原因を探す
  - **その後直した**（2026-10-09）: yomitoku はページごとに 2 つのスレッドの pool を作り直して読み、PyTorch は GPU で
    モデルを動かしたスレッドごとのメモリを、スレッドが終わっても返さなかった。worker で 1 つの pool を使い回させると、
    同じ 64 ページ × 20 回（1,280 ページ）で working set 1,689〜1,917MB の横ばいになった（読んだ内容・速さは同じ）。
    念のため、worker を 1,000 ページごとに起動し直すようにもした（`OcrConfig.worker_pages`）
- 正確さ（既定の設定）は 1,600 ページでも PaddleOCR 99.6%・yomitoku-lite 98.4%。yomitoku-lite の差は回したページ

  落とすもの、日付の誤り 82 は通帳の `13-03-28` → `3-031-28` のように先頭の 1 を落とすもの

### 照合の数を数えるコマンド（`ocr score-engines --agreement`）

### CPU の使い方とメモリ

`ocr run` は、エンジンを 1 つずつ、ページを 1 枚ずつ読む。CPU をどれだけ使うかは、エンジンが中で並列にするかで決まる。
worker のプロセスの CPU 使用率（100% がコア 1 つ分）を 15 秒ごとに記録した:

| エンジン | CPU 使用率 | 主に動く所 |
|---|---|---|
| ndlocr-lite | 275〜426% | CPU（onnxruntime がコアを 3〜4 つ使う） |
| paddleocr | 100〜117% | CPU のコア 1 つ |
| apple-vision | 約 87% | Neural Engine |
| yomitoku・yomitoku-lite | 30〜55% | GPU（MPS）。CPU は画像の下ごしらえ |

- **PaddleOCR は Mac ではコア 1 つしか使わない**: Mac の PaddlePaddle には oneDNN（Intel・AMD の CPU 向けの部品）が
  入っていない（`is_compiled_with_mkldnn` が False）。PaddleX は oneDNN がないと実行のしかたを `paddle` にし、
  `cpu_threads`（既定 10）を渡しても、使うのはコア 1 つだった（行列の計算は Apple の Accelerate につながっている）。
  そのため 1 ページ 7〜26 秒（請求書・明細が 20 秒前後、レシートが 7 秒）。Windows の CPU で落ちた oneDNN のエラーは、
  Mac では起きない
- PaddleOCR の worker のメモリは、ページの大きさで 5〜16GB を上下する（600dpi の明細で最大）。ページを読み終えると戻り、
  増え続けない

**yomitoku・yomitoku-lite を CPU で**（`--device cpu`、保存先を分けて `SCRIPTORIUM_DIR=data/ocr-cpu`、向きの判定あり）:

| エンジン | MPS | CPU |
|---|---|---|
| yomitoku | 99.3% / 100.0%、0.9 秒 | 99.3% / 100.0%、1.3 秒 |
| yomitoku-lite | 99.8% / 100.0%、0.7 秒 | 99.8% / 100.0%、0.8 秒 |

劣化ごとまで MPS と CPU で同じ数（Windows の GPU と CPU と同じ）。MPS が少し速いので、装置は既定の `auto` のままでよい。

### わかったこと

- **Mac でも全エンジンが動き、同じ書類なら Windows と同じ結果になる**（Tesseract を除く）
- **Mac でも主は yomitoku-lite（MPS）、照合役は PaddleOCR**（2026-10-09 に決めた）。Apple Vision は速い（0.4 秒）が、
  金額 94.8% で、マイナスの記号（`▲`・`△`）を読めない。PaddleOCR は Mac では 1 ページ 15 秒前後かかるが、明細のような
  月に数ページの書類なら困らない（遅くて困るのは本のような量のとき）。Windows と Mac で設定を同じにできる
  （エンジンは `yomitoku-lite,paddleocr`、向きの判定は `tesseract`）
- Apple Vision を照合役に使うなら、言語の補正を切る（数字が変わらなくなる）うえで、マイナスの
  記号を読めないことを照合で補う必要がある。今は使わない
- 装置は `auto`（MPS）のまま。yomitoku の結果は MPS と CPU で同じ

  カンマをピリオドに 73（`4,000` → `4.000` など）、数字の読み違い 5（`2,670` → `2,610` など、`7` を `1` に読むものが多い）。
  64 ページと同じ傾向
- yomitoku-lite と組ませた照合（`ocr diff-engines --digits`）では、数字のまとまり 6,573 のうち 267 が食い違う（Windows の
  yomitoku-lite と PaddleOCR の一覧は 35 件）。正解の行ごとに見ると、2 つが同じに読み違えたものは 0（yomitoku と
  yomitoku-lite では 5）

### 長い実行（yomitoku-lite、MPS）

同じ 64 ページを 1 つの worker で 20 回（1,280 ページ）読ませた。worker を起動し直す設定は切った
（`SCRIPTORIUM_WORKER_PAGES=0`）。worker のメモリ（RSS）を 1 分ごとに記録した。

| 読んだページ | 失敗 | 読むのにかかった時間 | 1 ページの時間（最初の 100 → 最後の 100） | worker の RSS（最小〜最大） |
|---|---|---|---|---|
| 1,280 | 0 | 15 分 | 0.66 → 0.65 秒 | 2,005〜3,387MB（増え続けない） |

- **止まらない・遅くならない・メモリを使い続けない**。RSS は読むページの大きさで上下し、最初の 1 分 3,096MB、
  最後 2,005MB
- Mac の GPU は CPU とメモリを共有するので、MPS が使うメモリは RSS に出ない。アクティビティモニタの「メモリ」と同じ値
  （`footprint` の `phys_footprint`）も、同じ 64 ページを 5 回（320 ページ）読ませて 20 秒ごとに見た:

  | 読んだページ | RSS | phys_footprint |
  |---|---|---|
  | 17 | 2,914MB | 6,618MB |
  | 105 | 2,040MB | 5,881MB |
  | 190 | 3,095MB | 6,941MB |
  | 250 | 3,131MB | 6,981MB |
  | 309 | 3,135MB | 6,987MB |

  phys_footprint は RSS より 3.8GB ほど多い（MPS の分）が、5,839〜6,987MB を上下するだけで増え続けない。Windows で直した
  メモリの増加（スレッドごとのメモリ）は、MPS でも起きていない

## Linux: 速さ（描くのと読むの割合、worker を複数）

`ocr run` は、ページを 1 枚ずつ描いて PNG に保存し、1 つの worker に読ませる（`design.ja.md` の「14. 速さ」）。速くする
前に、どこに時間がかかるかと、worker を複数起動すると速くなるかを測った。コアの多い PC と GPU のエンジンは
「Windows: 速さ」、それを受けて入れたもの（先読み・`--jobs`）の前と後もそちら。

### 条件

| 項目 | 内容 |
|---|---|
| 日付 | 2026-10-13 |
| 環境 | Linux（Ubuntu 24.04、コンテナ）、CPU 4 コア、GPU なし |
| エンジン | Tesseract 5.3.4（Ubuntu のパッケージ、`jpn+eng`、psm 3）、NDLOCR-Lite 1.0.0（onnxruntime 1.26.0） |
| 書類 | `ocr make-samples --count 1 --seed 1`（64 ページ、フォントは Noto Sans CJK）と、その請求書・明細の 300dpi・600dpi の画像を交互に 10 ページ並べた、画像だけの PDF（A4、JPEG） |
| 設定 | 既定（300〜600dpi）。向きの判定・前処理はなし |
| 測り方 | `ocr run` の関数（`runner.run` の中）に時計を付け、ページごとに、描く（pdfium・PIL）・PNG に保存・worker が読む（答えが返るまで）を分けた。worker を複数にするのは `ocr run` にまだないので、同じ `Worker` を N 個起動して（起動の時間は含めない）、描いておいた 20 ページ（300dpi の PDF の 10 ページ × 2）を分け合わせた |

### 描くのと読むの割合（1 ページの中央値）

| 書類 | 画像 | 描く | PNG に保存 | Tesseract が読む | NDLOCR-Lite が読む |
|---|---|---|---|---|---|
| 64 ページ（いろいろ） | 3.5MP | 0.05 秒 | 0.16〜0.17 秒 | 1.51 秒 | 2.39 秒 |
| A4 の PDF、300dpi | 8.7MP | 0.24 秒 | 0.19〜0.20 秒 | 1.83 秒 | 2.74 秒 |
| A4 の PDF、600dpi | 34.8MP | 0.98〜1.15 秒 | 0.75〜0.78 秒 | 5.92 秒 | 5.34 秒 |

描いて保存するのが 1 ページの時間に占める割合は、Tesseract で 14%・19%・23%、NDLOCR-Lite で 9%・14%・27%（上から順に）。
worker の起動は、Tesseract が 0.2 秒ほど、NDLOCR-Lite が 15〜19 秒（モデルを読み込む）。

### worker を複数: Tesseract（20 ページ）

| worker の数 | `OMP_THREAD_LIMIT=1` | 既定（OpenMP のスレッドを絞らない） |
|---|---|---|
| 1 | 0.61 ページ/秒（1 ページ 1.63 秒） | 0.61 ページ/秒（1.65 秒） |
| 2 | 1.20 ページ/秒（1.59 秒） | **0.016 ページ/秒（126.6 秒）** |
| 3 | 1.80 ページ/秒（1.58 秒） | 測らず |
| 4 | **2.42 ページ/秒（1.59 秒）** | 測らず |

1 ページの時間は、worker ごとに測ったもの。

### worker を複数: NDLOCR-Lite（20 ページ）

| worker × スレッド | ページ/秒 | 1 ページ（worker ごと） |
|---|---|---|
| 1 × 既定（全コア） | 0.40 | 2.47 秒 |
| 2 × 既定 | 0.39 | 5.11 秒 |
| 4 × 既定 | 0.34 | 11.41 秒 |
| 1 × 4 | 0.41 | 2.45 秒 |
| 2 × 2 | 0.48 | 4.18 秒 |
| 4 × 1 | **0.50** | 7.99 秒 |

スレッドを絞ったのは、worker を写して、ONNX Runtime の `intra_op_num_threads` と、NDLOCR-Lite が行を読むスレッドの数を
変えたもの（scriptorium の worker にはその設定がない）。

### 描くのを並べる（20 ページを描いて PNG に保存）

| | 300dpi | 600dpi |
|---|---|---|
| 1 スレッド | 2.45 ページ/秒 | 0.59 ページ/秒 |
| 2 スレッド（pdfium は 1 つずつ） | 4.61 | 1.12 |
| 4 スレッド（pdfium は 1 つずつ） | 4.50 | 1.11 |
| 2 プロセス | 4.12 | 1.17 |
| 4 プロセス | **8.42** | **2.48** |

pdfium はスレッドから同時に使えないので、スレッドでは描くところをロックで 1 つずつにした（PNG に保存は同時）。

### わかったこと

- **描いて保存するのは、1 ページの 1〜3 割**。次のページを読んでいる間に描いておけば（先読み）、CPU のエンジンで
  1.1〜1.3 倍ほど速くなる計算。GPU で 1 ページ 0.5〜1 秒のエンジンでは、割合はもっと大きいはず（測っていない）
- 600dpi では、PNG に保存するのに描くのと同じくらいかかる（34.8MP、`compress_level=1`）
- **Tesseract は worker の数だけ速くなる**: `OMP_THREAD_LIMIT=1` で 4 つなら 4.0 倍（コア 4 つ）。1 つでも、OpenMP の
  スレッドは速さに効いていない（1.65 秒 → 1.63 秒）
- **Tesseract を、OpenMP のスレッドを絞らずに 2 つ同時に動かすと、1 ページ 1.6 秒 → 127 秒と大きく遅くなる**。スレッドが
  コアを取り合って待ち合う。複数起動するなら（`ocr run` を 2 つ同時に流すのも）`OMP_THREAD_LIMIT=1` が要る
- **NDLOCR-Lite は 1 つで全コアを使う**: 既定のまま複数起動しても速くならない（4 つでかえって遅い）。worker ごとに
  スレッドを 1 つに絞って 4 つ起動すると 1.24 倍。起動に 15〜19 秒かかるので、worker を増やすのは長い実行向き
- **描くのをスレッドで並べても 2 倍ほどで止まる**: pdfium を 1 つずつにすると、描く分が並ばない。プロセスならコアの数
  だけ速くなる（4 つで 3.4〜4.2 倍）。CPU のエンジンを多く起動すると、描くのも同じコアを取り合う
- この環境（4 コア、GPU なし）・架空の書類での値。コアの多い PC や GPU のエンジンでは、それぞれ測り直す。64 ページの
  Tesseract は、一部が NDLOCR-Lite の環境作り（`uv sync`）と同時に動いた

### 再現のしかた

```bash
uv run scriptorium make-samples data/speed --count 1 --seed 1
uv run scriptorium run data/speed -e tesseract -e ndlocr-lite --reread
# Tesseract を N 個同時に（worker も 1 ページごとに同じコマンドを動かす）。pages/ は描いておいた PNG
ls pages/*.png | OMP_THREAD_LIMIT=1 xargs -P 4 -I{} tesseract {} stdout -l jpn+eng --psm 3 tsv > /dev/null
```

A4 の PDF は、`make-samples` の `invoice-1-300.png`・`statement-1-300.png`（600dpi も同じ）を PIL で 10 ページの PDF に
した（`save_all=True`、`resolution` に dpi）。描く・保存・読むの内訳と、worker を N 個にした速さは、`runner` の関数と
`Worker` をそのまま使う小さなスクリプトで測った（`xargs` の行は、Tesseract についてそれとほぼ同じ数になる: 20 ページが
1 つで 28 秒、4 つで 7.6 秒）。

| NDLOCR-Lite | 45.9 秒 | 40.5 秒 | 1 |

どのエンジンも、40 ページすべてで読んだ内容（文字・位置・確からしさ）が前と同じ。yomitoku・NDLOCR-Lite は、モデルの
読み込み（約 20 秒・約 9 秒）を除くと 1.2〜1.3 倍ほど。

### わかったこと

- **エンジンは、worker の増やし方で 3 つに分かれる**:
  - 増やすと速くなる: Tesseract（1 スレッドで、物理コアの数まで）、Windows の OCR、CPU の PaddleOCR（ただし CPU と
    メモリを使い切る）
  - 1 つで全コアを使うのがいちばん速い: NDLOCR-Lite、CPU の yomitoku。スレッドを絞って数を増やしても速くならない
  - GPU 1 枚に 1 つ: GPU のエンジン
- **先読みは、どのエンジンにも効く**（1.17〜1.97 倍の見込み）。読むのが速いエンジン・高い解像度ほど効く。Windows の
  OCR は、読むのが描くのと同じくらい速い
- **描くのはプロセスで並べる**: スレッドでは 1.4 倍ほどで止まる。速いエンジンを複数の worker で読むと、描くのが
  1 つでは追いつかない（Windows の OCR は 2 つから）
- **GPU のエンジンの CPU のスレッドは 1 つでよい**: CPU の使用率が 5〜6 割から 1 割になり、遅くならない
- **増やして速くなるエンジンは、メモリをあまり使わない**（worker 1 つ 1GB 以下）。メモリを多く使うエンジン（CPU の
  yomitoku・PaddleOCR）は、増やしても速くならないか、CPU を使い切る
- この PC（16 コア、GPU 1 枚）・架空の書類での値。コアの少ない PC は「Linux: 速さ」（4 コア）を、Mac は「Mac: 速さ」を見る

### 再現のしかた

して、1 ページ目の隅に小さな点をファイルごとに違う場所に描いたもの（中身の違うファイルにするため）。描く・保存・読むの

  `auto` が 1 つにするのは合っている。PaddleOCR は A4 の 300dpi の PDF では 1 ページ 21 秒かかる（正確さの書類は 14 秒）
- 値は、この Mac・架空の書類・40〜64 ページのもの

## Linux（VMware の仮想マシン）: master（v0.3.0 の前）での測り直し

並列化（`--jobs`、先読み）とその後の修正を入れた `master` で、Linux の全エンジンの動作と、正確さ・速さを測った。Linux でこれまで
確かめていたのは、コンテナ（4 コア）の Tesseract と NDLOCR-Lite だけだった。GPU は使えないので、全エンジンが CPU で動く。
v0.3.0 を出す前の確認を兼ねる。

### 条件

| 項目 | 内容 |
|---|---|
| 日付 | 2026-10-17 |
| scriptorium | `master` の 22d53e0（v0.2.0 のあと 17 コミット）、Python 3.14.8 |
| 環境 | VMware Workstation Pro 26H1（26.0.0.25388281、Windows 11 のホスト）上の Ubuntu 24.04.5 LTS（カーネル 7.0.0-38）。ホストの CPU は AMD Ryzen 9 5950X（物理 16 コア・論理 32 スレッド）。GPU のパススルーは使わない |
| 仮想マシン | 8 vCPU（1 ソケット × 8 コア）、RAM 16GB。ほかに 4 vCPU（RAM 16GB）と 16 vCPU（RAM 32GB）で速さだけ測った |
| エンジン | Tesseract 5.3.4（`jpn+eng`、psm 3）、NDLOCR-Lite 1.0.0、yomitoku 0.15.0（yomitoku・yomitoku-lite。PyTorch は PyPI の CPU 版）、PaddleOCR 3.7.0（PaddlePaddle 3.3.1、CPU） |
| 装置 | すべて CPU |
| 書類 | `ocr make-samples --count 1 --seed 1`（4 種類 × 劣化 16 通り = 64 ページ）を、この仮想マシンで作った。フォントは、`fonts-noto-cjk` を入れて `ocr make-samples` が選んだ Linux の日本語のフォント。Windows・Mac の 64 ページは游ゴシックの書類なので、**同じ書類ではない** |
| 設定 | 既定（向きの判定も前処理もなし。worker の数は `--jobs auto`） |

vCPU は仮想マシンの論理スレッドで、ホストの物理コアとは限らない。この表の速さは、すべて「仮想マシン上の値」で、ホストでほかの
作業はしていない。worker の環境（`workers/`）は、`uv sync` で `uv.lock` どおりにした。

### 動作

`ocr check-engines` は、Tesseract・NDLOCR-Lite・yomitoku・yomitoku-lite・PaddleOCR のすべてで動いた（サンプル 1 枚の金額は、
yomitoku・yomitoku-lite・PaddleOCR が 12 個すべて、NDLOCR-Lite が 11 個、Tesseract が 10 個）。Apple Vision と Windows の OCR は、
「macOS のみ」「Windows のみ」と理由が出て、飛ばされた。`workers/paddleocr` の `paddlepaddle-gpu` は、CPU だけの Linux でも
そのまま入って動いた。

起動の時間（モデルを読み込むまで）は、yomitoku 62.0 秒、PaddleOCR 27.3 秒、yomitoku-lite 20.1 秒、NDLOCR-Lite 5.7 秒、
Tesseract 0.1 秒。

### 正確さ（64 ページ）

`ocr make-samples --count 1 --seed 1` の 64 ページ（4 種類 × 16 通りの劣化）を、`-e all` で読んだ。失敗は 0 ページ。

| エンジン | 金額の完全一致 | 日付の完全一致 | 文字の誤り率 | 読み落とした行 |
|---|---|---|---|---|
| PaddleOCR | 99.8% | 99.7% | 0.9% | 2 / 2672 |
| yomitoku-lite | 98.9% | 99.2% | 0.9% | 0 / 2672 |
| yomitoku | 96.3% | 95.1% | 3.2% | 0 / 2672 |
| Tesseract | 76.2% | 88.3% | 18.7% | 224 / 2672 |
| NDLOCR-Lite | 69.1% | 69.8% | 24.5% | 87 / 2672 |

- 向きを正す設定を付けていないので、逆さまの書類（`turned180`）は、yomitoku が金額 44.1%、yomitoku-lite が 86.4%、NDLOCR-Lite と
  Tesseract が 0% だった。PaddleOCR は 98.3%
- Tesseract は、影のある書類（`shadow`）で金額 44.1%、写真風（`photo`）で 0.0% だった

この読み取りの「1 ページの時間」は載せない。同じ読み取りを 2 つ同時に動かしたため、時間が長く出ている（読んだ内容は
同じ）。時間は、次の「速さ」の測定だけを見る。

### 速さ（`ocr run`、40 ページ、8 vCPU）

「Windows: 速さ」と同じ作りの 40 ページ（A4 の 300dpi の PDF 4 つ、各 10 ページ）を、エンジンごとに `--reread` で読み直した。
時間はコマンド全体（worker の起動を含む、秒）で、3 回の中央値。3 回のぶれは 1 秒以内だった。

| `--jobs` | Tesseract | NDLOCR-Lite |
|---|---|---|
| 1 | 34.0 | **40.4** |
| 2 | 18.2 | 44.6 |
| 4 | 10.0 | 47.2 |
| 6 | 7.6 | 測らず |
| 8 | **6.9** | 測らず |
| auto | 7.8（6 worker） | 41.8（1 worker） |

`auto` は、8 コアから 2 つを残して、Tesseract を 6 worker にした。8 worker より 1 割ほど遅いだけで、仮想マシンのほかの
作業に空きが残る。

### vCPU の数を変える（4・8・16）

仮想マシンの電源を切って vCPU の数（と RAM）を変え、同じ 40 ページを測った。4 vCPU は RAM 16GB、16 vCPU は 32GB。時間は
コマンド全体（秒）で、3 回の中央値。

| `--jobs` | Tesseract 4 vCPU | Tesseract 8 vCPU | Tesseract 16 vCPU |
|---|---|---|---|
| 1 | 34.0 | 34.0 | 34.3 |
| 2 | 18.3 | 18.2 | 測らず |
| 3 | 13.7 | 測らず | 測らず |
| 4 | **12.2** | 10.0 | 10.1 |
| 8 | 測らず | **6.9** | 5.9 |
| 12 | 測らず | 測らず | 5.1 |
| 16 | 測らず | 測らず | **4.7** |
| auto | 13.8（3 worker） | 7.8（6 worker） | 5.1（12 worker） |

| `--jobs` | NDLOCR-Lite 4 vCPU | NDLOCR-Lite 8 vCPU | NDLOCR-Lite 16 vCPU |
|---|---|---|---|
| 1 | 47.6 | 40.4 | 38.3 |
| auto（1 worker） | 45.8 | 41.8 | 38.4 |

- `auto` の worker の数は、4 コアで 3、8 コアで 6、16 コアで 12 だった（コアの数から 4 分の 1 を空ける）
- Tesseract は、vCPU の数に合わせて速くなる。worker の数がコアの数のとき、1 worker に対して 4 vCPU で 2.8 倍、8 vCPU で
  4.9 倍（8 worker）、16 vCPU で 7.3 倍（16 worker）。`auto` はどれも最速より 1 割ほど遅いだけ（2.5 倍、4.4 倍、6.7 倍）
- 16 vCPU でも、倍率はコアの数の半分ほど。ホストは 16 コア・32 スレッドで、16 vCPU はホストの論理スレッドに載るため、
  物理 16 コア分の力は出ていない
- NDLOCR-Lite は 1 worker のままで、vCPU を増やすと 47.6 → 40.4 → 38.3 秒と少しずつ速くなる（1 つの worker がコアを
  まとめて使う）

### わかったこと

- **Linux で、5 つのエンジンがすべて、CPU で動いた**。PaddleOCR も、Linux の CPU でそのまま入った
- **worker を増やして速くなるのは Tesseract**。8 worker で 4.9 倍、`auto`（6）で 4.4 倍。NDLOCR-Lite は増やすと遅くなり
  （4 worker で 0.86 倍）、`auto` が 1 つにするのは合っている。どちらも、Windows・Mac と同じ傾向
- vCPU の数を変えても、**`auto` の worker の数は、コアの数に合った**（上の表）
- **Windows・Mac と同じ書類ではないので、正確さの数字は直接は比べられない**。Windows と Mac は同じ 64 ページを読み、金額の完全一致は yomitoku 96.5%、yomitoku-lite 99.6%、PaddleOCR 99.7%、NDLOCR-Lite 80.8% で、2 つの環境の数字が同じだった。Linux（CPU）は 96.3%、98.9%、99.8%、69.1%。yomitoku・yomitoku-lite・PaddleOCR は近いが、NDLOCR-Lite は 11 ポイント低い（日付 87.2% → 69.8%、文字の誤り率 15.8% → 24.5%）。Tesseract は版も違う（5.3.4 と 5.5.3）。NDLOCR-Lite の差が、書類（フォント）のせいか Linux のせいかは、確かめていない。Windows の 64 ページを Linux に写して読めば、分かる
- 値は、この仮想マシン・架空の書類・40 ページのもの。yomitoku・PaddleOCR の速さは、この仮想マシンでは測っていない
